# Archivio PC: modifica amministrativa dei dati

**Data:** 25 novembre 2026  
**Stato:** disegno approvato  
**Ambito:** `/apps/archivio-pc`

## Obiettivo

Rendere l'inventario dei PC modificabile direttamente dall'app dagli amministratori di truedesign.app, mantenendo il link pubblico completamente in sola lettura. Le modifiche devono essere condivise immediatamente, senza commit o deploy, e devono aggiornare automaticamente ordinamento, schede e valutazioni prestazionali.

## Decisioni

- Supabase diventa l'unica fonte dati operativa dell'inventario.
- I 51 record correnti vengono importati dal JSON con una migrazione idempotente.
- Il pubblico continua a vedere la stessa interfaccia senza controlli amministrativi.
- Solo i profili con `profiles.is_admin = true` possono creare, modificare o archiviare un PC.
- I PC non vengono cancellati definitivamente: l'azione disponibile è `Archivia`.
- Il punteggio non viene salvato nel database: viene sempre ricalcolato dai componenti e dal profilo assegnato.
- Il JSON corrente resta nel repository come sorgente della migrazione iniziale, ma non viene letto a runtime dopo il passaggio a Supabase.

## Modello dati

### Tabella `pc_assets`

La tabella conserva i dati già rappresentati da `PcRecord`:

- `id bigint generated by default as identity primary key`
- `profilo text not null`, limitato a `Ufficio`, `Tecnico`, `Grafica`, `3D avanzato`
- `nome_dispositivo text not null default ''`
- `assegnatario text not null`
- `tipologia text not null`
- `marca text not null default ''`
- `modello text not null default ''`
- `anno text not null default ''`
- `numero_serie text not null default ''`
- `processore text not null default ''`
- `core_processore text`
- `processori_logici text`
- `ram text not null default ''`
- `gpu text not null default ''`
- `schermo text not null default ''`
- `archiviazione text not null default ''`
- `sistema_operativo text not null default ''`
- `versione_os text not null default ''`
- `data_installazione_os text not null default ''`
- `data_acquisto text not null default ''`
- `prezzo_acquisto text`
- `venditore text`
- `articolo_acquisto text`
- `note text not null default ''`
- `area text not null default ''`; stringa vuota significa `Da assegnare`
- `foto text not null default ''`
- `is_archived boolean not null default false`
- `updated_on date not null default current_date`
- `updated_at timestamptz not null default now()`
- `updated_by uuid references auth.users(id) on delete set null`
- `created_at timestamptz not null default now()`

Gli identificativi correnti da 1 a 51 vengono preservati durante l'importazione. Al termine della migrazione la sequenza identity viene riallineata al massimo identificativo presente.

### Sicurezza del database

La tabella usa RLS e non concede scritture dirette al client anonimo o autenticato. Letture e scritture passano esclusivamente dal server Next.js tramite service role, mai esposta nel browser.

Il fatto che l'app sia pubblica non concede alcun permesso sul database. La pagina server legge soltanto i record con `is_archived = false`. Prima di ogni scrittura una server action:

1. recupera la sessione corrente;
2. verifica `profiles.is_admin` con il client amministrativo;
3. valida e normalizza tutti i campi;
4. esegue la modifica impostando `updated_by`, `updated_at` e `updated_on`.

## Architettura applicativa

### Lettura

`page.tsx` diventa una pagina dinamica server-side. Carica da Supabase i PC attivi, li converte nel tipo applicativo e li passa ad `ArchivePc`. Nella stessa richiesta determina se l'utente corrente è amministratore e passa un semplice booleano `canEdit` al client.

La funzione di mapping tra riga Supabase e `PcRecord` è isolata in un modulo dati. `updated_on` viene formattato come `gg/mm/aaaa` nel campo applicativo `aggiornata`.

Il modello passato al client include inoltre `updated_at` come token tecnico di versione separato dai campi mostrati nella scheda. Non entra nel calcolo prestazionale e viene usato soltanto per il controllo di concorrenza durante il salvataggio.

Se la lettura del database fallisce, la pagina mostra un messaggio di indisponibilità con possibilità di riprovare. Non usa silenziosamente il JSON, perché ciò mostrerebbe dati vecchi e creerebbe due fonti concorrenti.

### Scrittura

Le server action dell'app espongono tre operazioni:

- `createPcAsset(input)` per aggiungere un PC;
- `updatePcAsset(id, input)` per modificare un PC esistente;
- `archivePcAsset(id)` per nasconderlo dall'inventario senza cancellarlo.

Ogni operazione restituisce un risultato discriminato `{ ok: true }` oppure `{ ok: false, error }`. Dopo una scrittura riuscita viene eseguito `revalidatePath('/apps/archivio-pc')`; il client chiude il form e chiama `router.refresh()`.

### Valutazione prestazionale

`assessPerformance` continua a essere una funzione pura. Dopo il refresh riceve i nuovi componenti e ricalcola voto, attendibilità, dati mancanti e priorità di sostituzione. Il database non contiene punteggi duplicati o potenzialmente obsoleti.

## Interfaccia amministrativa

La vista pubblica non cambia. Se `canEdit` è vero:

- nell'intestazione compare il comando compatto `Aggiungi PC`;
- nella scheda dettagliata compare un'icona matita con etichetta accessibile `Modifica PC`;
- il form si apre in un dialogo dedicato sopra la scheda, con scroll interno e focus gestito;
- l'azione `Archivia` è visivamente secondaria e richiede una conferma esplicita con il nome del PC.

Il form è suddiviso in gruppi brevi:

1. **Assegnazione:** assegnatario, nome dispositivo, reparto, profilo, tipologia.
2. **Hardware:** marca, modello, anno, seriale, CPU, core, processori logici, RAM, GPU, schermo, archiviazione.
3. **Sistema:** sistema operativo, versione e data di installazione.
4. **Acquisto:** data, prezzo, venditore e articolo.
5. **Note e immagine:** note e chiave dell'immagine esistente; l'immagine è facoltativa per i nuovi PC.

Reparto e tipologia propongono i valori esistenti ma consentono una nuova voce testuale. Il profilo è sempre uno dei quattro valori ammessi. Il form usa i dati correnti come valori iniziali e segnala gli errori vicino al relativo campo e in un riepilogo generale.

## Validazione

- `assegnatario`, `tipologia` e `profilo` sono obbligatori;
- i campi di testo vengono sottoposti a `trim`;
- i testi brevi hanno limite di 200 caratteri, le note di 2.000;
- il profilo deve appartenere all'elenco autorizzato;
- l'ID ricevuto dalle azioni deve essere un intero positivo;
- una modifica o archiviazione di un ID inesistente restituisce un errore sicuro;
- gli errori Supabase e i dettagli interni vengono registrati sul server ma non esposti al browser.

Non vengono imposti formati rigidi a prezzo e date storiche nella prima versione, per non rendere impossibile la migrazione dei valori parziali già presenti. `updated_on` è invece sempre una vera data del database.

## Stati e concorrenza

Durante il salvataggio i pulsanti vengono disabilitati e mostrano uno stato di avanzamento. Un errore mantiene aperto il form e conserva i valori inseriti.

Per evitare sovrascritture silenziose, l'update invia anche il valore `updated_at` letto all'apertura. La query aggiorna la riga soltanto se quel valore non è cambiato. In caso contrario il form comunica che un altro amministratore ha modificato il PC e richiede di ricaricare i dati.

## Accessibilità e responsive

- dialogo con titolo associato, focus iniziale e chiusura tramite `Esc`;
- etichette esplicite per tutti i campi e le icone;
- errori annunciati con `aria-live`;
- area cliccabile minima di 44 px;
- su mobile il form occupa quasi tutto lo schermo e scorre internamente senza muovere la pagina sottostante;
- il blocco dello scroll viene rimosso sempre alla chiusura e allo smontaggio.

## Test

### Dominio e dati

- mapping completo da riga Supabase a `PcRecord`;
- conversione corretta di `updated_on`;
- esclusione dei record archiviati;
- ricalcolo del punteggio dopo la modifica di CPU, RAM, GPU o profilo;
- migrazione con 51 PC, identificativi preservati e nessun server o macchina virtuale.

### Server action

- utente anonimo rifiutato;
- utente autenticato non amministratore rifiutato;
- amministratore autorizzato;
- validazione dei campi e messaggi sicuri;
- create, update con controllo concorrenza e archive;
- valorizzazione di `updated_by`, `updated_at` e `updated_on`.

### Interfaccia

- nessun comando di modifica per pubblico e utenti non amministratori;
- comandi visibili agli amministratori;
- popolamento del form con i dati della scheda;
- salvataggio, errore, conflitto e conferma archiviazione;
- refresh della scheda e del punteggio dopo il salvataggio;
- scroll interno del dialogo su desktop e mobile.

## Migrazione e rilascio

1. Creare tabella, vincoli, indici e policy in una migrazione Supabase.
2. Importare i 51 record correnti in modo idempotente e riallineare l'identity.
3. Implementare il modulo dati e verificare la parità con il JSON.
4. Implementare server action e relativi test di autorizzazione.
5. Collegare la lettura Supabase alla pagina.
6. Aggiungere i controlli e il form amministrativo.
7. Eseguire test completi, typecheck e build.
8. Applicare la migrazione al progetto Supabase, pubblicare su `main` e verificare:
   - accesso anonimo in sola lettura;
   - modifica riuscita con profilo amministratore;
   - modifica rifiutata per un utente non amministratore;
   - ricalcolo del voto dopo una modifica hardware;
   - assenza dei PC archiviati dalla vista pubblica.
